# 類股輪動看板（台股上市櫃 + 美股）

用官方公開資料，回答一個問題：**現在哪些產業的體質正在變好、哪些在變差。**

它刻意不做的事：不預測股價、不給買賣點、不做個股推薦。

| 市場 | 類股數 | 價格來源 | 基本面來源 | 籌碼面 |
|---|---|---|---|---|
| 台股 | 32 | 證交所類股指數 | 上市：證交所 OpenAPI<br>上櫃：櫃買 OpenAPI + 公開資訊觀測站 | 三大法人、融資餘額（僅上市） |
| 美股 | 11 | Yahoo Finance（SPDR 類股 ETF） | SEC XBRL frames | 無（美國沒有等同的公開日資料） |

全部免金鑰、免註冊。

## 快速開始

需求：Windows + Python 3.10 以上。

```
pip install -r scripts/requirements.txt
```

> `requirements.txt` 刻意放在 `scripts/` 而不是根目錄。放根目錄的話，Vercel 的框架自動偵測會把這個專案當成 Python 應用，去找 `app.py` 之類的入口點然後建置失敗——但這其實是純靜態網站，Python 只在本機和 GitHub Actions 產生 JSON。

然後雙擊：

1. **`update.cmd`** — 抓資料並計算分數。首次執行約 20 分鐘（要回補 2.5 年的類股指數歷史），之後每次約 1 分鐘。
2. **`serve.cmd`** — 啟動本機網頁伺服器，瀏覽器會自動開啟 <http://localhost:8749/>。

> 不能直接雙擊 `web/index.html`。瀏覽器的安全限制會讓它讀不到 JSON 資料檔，一定要透過 `serve.cmd`。

> `.cmd` 檔案裡刻意全部用英文。cmd.exe 是用系統的 OEM 編碼（繁中 Windows 是 cp950）讀批次檔，檔案裡若有 UTF-8 中文會被拆成亂碼當成指令執行。中文輸出一律交給 Python。

美股資料要另外跑（`update.cmd` 已包含）：

```bash
python scripts/build_us.py
```

首次執行會下載一份約 85 MB 的 SEC 季度批次檔（用來取得每家公司的 SIC 產業代碼），之後有快取不會重抓。

## 部署（Vercel）

專案已經是 git repo，也附好 `vercel.json` 與 GitHub Actions 排程。要讓家人朋友能看：

1. 到 <https://github.com/new> 建立一個名為 `sector-rotation` 的 repo（**不要**勾選 Add README / .gitignore，保持全空）
2. 在專案資料夾執行 `git push -u origin main`
3. 到 <https://vercel.com/new> 匯入這個 repo，設定會自動從 `vercel.json` 讀取

之後 `.github/workflows/update-data.yml` 會在每個平日台北時間 19:30 自動更新資料並 push，Vercel 收到 push 就會重新部署。也就是說網站會自己更新，你不用做任何事。

### 部署設定的兩個坑

**這是純靜態網站，不是 Python 應用。** `scripts/` 底下的 Python 只在本機和 GitHub Actions 執行，用來產生 `web/data/*.json`，不會在 Vercel 上跑。所以：

1. `requirements.txt` 放在 `scripts/` 而不是根目錄。放根目錄會觸發 Vercel 的框架自動偵測，把專案當成 Python 應用去找 `app.py` 之類的入口點，然後建置失敗。
2. `vercel.json` 用 `"framework": null` 搭配空的 `buildCommand` 與 `installCommand`，明確關掉建置流程，只把 `web/` 當靜態輸出。這一項是必要的——專案第一次匯入時 Vercel 若已經把框架記成 `python`，之後就算移走 `requirements.txt` 也不會自動改回來。

另外 `vercel.json` **不接受任何額外的鍵**（schema 是 `additionalProperties: false`），連 `"// 註解"` 這種假鍵都會讓整份設定驗證失敗、所有設定被忽略。想寫說明就寫在這裡。

## 「短、中、長期」怎麼定義

網路上沒有單一權威定義，常見的有兩套，用途不同：

**A. 投資期間（Investment Horizon）— 理財／法規語境**

美國 SEC 與 FINRA 在「適合性原則」中把投資期間列為推薦商品的關鍵因素，業界慣用切法是：短期 0～3 年、中期 3～10 年、長期 5～10 年以上。

**B. 道氏理論（Dow Theory）— 走勢語境**

主要趨勢 1 年以上、次級趨勢 3 週～3 個月、短期趨勢 3 週以內（被視為雜訊）。

**C. 本專案採用的定義**

上面兩套都不是為「基本面驅動的類股輪動」設計的。真正該決定週期的，是**資料本身的更新節奏**：

| 期間 | 範圍 | 對應的資料節奏 | 主導面向 |
|---|---|---|---|
| 短期 | 1～3 個月 | 月營收（每月 10 日前公告）、三大法人日資料 | 籌碼面主導 |
| 中期 | 3 個月～2 年 | 季報（約 5/15、8/14、11/14、3/31 公告） | **基本面主導** |
| 長期 | 2 年以上 | 多年期獲利品質、產業結構 | 純基本面 ＋ 估值 |

### 為什麼短期不能用基本面

**基本面資料一季才更新一次。** 所以「用基本面預測一個月內的類股輪動」在資訊上是不成立的——那段期間根本沒有新的基本面訊息進來，任何看起來有效的訊號都是技術面偽裝的。

本專案的短期分頁因此明確以籌碼流向與價格動能為主，基本面只取每月更新的營收動能。畫面上會標示清楚，避免使用者誤以為短期分數有財報依據。

## 方法論

### 類股怎麼分

用證交所官方產業分類，共 **32 個類股**（排除存託憑證）。每個類股都對應一檔官方發布的類指數，用於計算相對強度。

刻意排除 5 檔**複合指數**（電子工業、塑膠化工、機電、水泥窯製、化學生技醫療），因為它們是多個產業的合併，納入排名會重複計算。

### 指標

| 面向 | 指標 | 資料來源 | 更新頻率 |
|---|---|---|---|
| 基本面 | 月營收年增率、營收動能加速度、營收成長家數占比、累計營收年增率 | `t187ap05_L` | 每月 |
| 基本面 | 營業利益率、稅後淨利率、ROE（年化）、獲利家數占比 | `t187ap14_L`、`t187ap07_L_*` | 每季 |
| 估值 | 本益比、股價淨值比、現金殖利率（皆取產業中位數） | `BWIBBU_ALL` | 每日 |
| 籌碼 | 外資買超佔股本比、投信買超佔股本比、融資餘額增減 | `T86`、`MI_MARGN` | 每日 |
| 技術 | RS-Ratio、RS-Momentum、20/60/120 日超額報酬 | `MI_INDEX` 歷史 | 每日 |

**「營收動能加速度」** = 當月營收年增率 − 累計營收年增率。當月表現比全年趨勢好，代表產業正在加速，這通常比絕對成長率更早反映轉折。

**籌碼面的正規化**用「淨買超股數 ÷ 該產業總發行股數」，意思是「法人這段期間買走了該產業幾 % 的股本」。這樣跨產業可直接比較，而且不需要估市值，避開股價與股本單位換算的誤差。

**季報是累計數，不是單季。** 證交所 `t187ap14_L` 的「季別 = 2」指的是**累計至第 2 季**（即半年報），不是第 2 季單季。已用台積電對帳確認：115Q2 營收 2.40 兆 ≈ 月營收前 7 個月累計 2.87 兆 × 6/7。因此 ROE 年化時要乘 `4 / 累計季數`，寫死乘 4 會在半年報時高估一倍。這是接這份資料很容易踩到的坑。

### 分數怎麼算

1. 每個指標先做**跨產業的穩健標準化**：`(x − 中位數) / (1.4826 × MAD)`，裁切到 ±2.5。
   用 MAD 而不是標準差，是因為台股常出現單一產業獲利暴衝（航運、記憶體），
   用標準差會讓其他 30 個產業全部擠成一團看不出差別。
2. 依期間加權合成（權重見 `scripts/build.py` 的 `HORIZONS`）。
3. 缺資料的指標一律當成**與同業中位數相同**（z = 0），也就是分母用完整權重，不是實際用到的權重。

   > 這裡踩過一次坑：一開始的作法是把缺漏指標的權重「攤回」給有資料的指標。結果金融保險業因為季報全缺、只剩下便宜的估值指標，在最看重獲利品質的**長期榜衝到第 3 名**——等於把「不知道」變成了「很好」。改成中性填補後，缺資料會把分數拉向中間，這才是誠實的行為。前端對覆蓋率低於 80% 的類股會直接標示。
4. 最後轉成 **0～100 的相對排名百分位**。

> **分數是相對的，不是絕對的。** 80 分代表「在這 32 個類股裡排前 20%」，不代表會漲。全部類股都在跌的時候，還是會有人拿 100 分。

### RRG（相對輪動圖）

採用 Julius de Kempenaer 的 JdK RS-Ratio / RS-Momentum 方法，以發行量加權股價指數為基準，60 個交易日滾動窗格。四象限：

- **領先**（右上）：強，而且還在轉強
- **轉弱**（右下）：仍強，但動能正在流失
- **改善**（左上）：仍弱，但動能開始回升
- **落後**（左下）：弱，而且持續走弱

典型輪動是順時針：改善 → 領先 → 轉弱 → 落後。

## 已知限制

**這些是真實的資料限制，不是還沒做完的功能。**

1. **金融保險業的季報缺漏。** 金控／銀行／證券的損益表在證交所 OpenAPI 目前是空的（30 家只有 2 家有資料）。該產業因此只採用月營收與籌碼面，季度獲利指標留白，前端以「季報缺」標記。
2. **季報沒有去年同期欄位。** 月營收 API 自帶去年同月數字可直接算年增率，但季報只有當期。所以目前的季度指標是**水準值**（營益率、ROE 的高低），不是**變化值**（比去年進步多少）。每季執行一次 `update.cmd` 就會自動累積，跑滿四季後可再加上季度年增率。
3. **只涵蓋上市（TWSE），不含上櫃（TPEx）。** 上櫃有自己的一套 API，格式相近但端點不同，要另外接。
4. **RRG 需要足夠歷史。** 第一次執行前 RRG 圖是空的，`update.cmd` 跑完才會出現。
5. **證交所 OpenAPI 只回傳最新一期。** 所以財報／營收無法回補歷史，只能從現在開始累積。價格歷史則可以回補（`backfill.py` 在做的事）。

## 專案結構

```
scripts/
  twse.py       證交所資料存取層（含快取與流量控制）
  sectors.py    產業別 <-> 類指數對照表
  fetch.py      抓最新一期全市場快照
  backfill.py   回補類股指數歷史（RRG 需要）
  chips.py      三大法人彙總到產業層級
  build.py      計分引擎 -> web/data/dashboard.json
web/
  index.html    看板（單一檔案，無外部相依）
  data/         產出的 JSON
data/
  cache/        API 回應快取，重跑不會重複打 API
  snapshot/     最新一期快照
  history/      累積的時間序列
```

### 要調整權重

改 `scripts/build.py` 裡的 `HORIZONS`，每個期間的權重加總為 1，改完重跑 `python scripts/build.py` 即可（不用重抓資料）。
